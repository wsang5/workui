# 质检作业模式 + 智能抽检

## Context（为什么做）

A/B 评测模板已支持标注员填写考点结论/备注。现在需要一个**质检阶段**：质检员复核标注员填得对不对，按整行给「通过/不通过」结论，结果写回表格新列；并按标注员统计正确率；为减少质检工作量，引入**智能抽检算法**——先抽一小批，达标就放行整批，不达标才追加抽检。

本期只做**质检**（标注暂不急）。涉及表：当前 A/B 评测模板（`...PN2msqf8bhMsSOtmPr0cb4pjnmM?sheet=1cQCKs`）。

## 已确认的需求

1. **作业模式**：在 A/B 模板上新增「质检模式」（标注模式本期不做）。页面顶部可切换。
2. **登录**：进页面输入名字即可（无密码），作为质检人身份，存 localStorage + 随写入提交。
3. **质检粒度**：整行一个结论：通过 / 不通过。
4. **正确率（通过率）**：按标注员（取自表格「评测人」列）统计。**正确率 = 通过数 / 已检数**（越高越好）。内部缺陷率 `d/n`（不通过/已检）仅供 SPRT 判定使用，不作为看板「正确率」展示，避免方向写反。
5. **质检写新列**（工具自动建列，写在表头右侧空列并补列名）：
   - `质检结论`（通过/不通过）
   - `质检意见`（文本，可空）
   - `质检人`（当前登录名）
   - `质检时间`（写入时间戳）
6. **防重复**：一条被质检后打「已检」标记，默认不再分配给别人（软提示，非强锁）。
7. **统计入口**：复用现有「问题分布」页，质检模式下切换为「质检统计」视图。
8. **智能抽检**：分阶段抽检算法，目的是尽量少检。详见下节。

## 智能抽检算法（核心）：SPRT 序贯概率比检验

把每个标注员的全部作业看作一个「批次」，逐条质检并用 **SPRT（Wald 序贯概率比检验）** 实时判定。SPRT 在给定 α、β 下平均抽样量最小（Wald-Wolfowitz 最优性）——即"既要抓出低质量、又尽量少检"的理论最优解。

### 四个参数（页面可调，给默认值）

| 参数 | 含义 | 默认 |
|---|---|---|
| `p1` (AQL) | 可接受正确率，高于它算"好" | 0.90 |
| `p0` (RQL/LTPD) | 不可接受正确率，低于它必须拦 | 0.80 |
| `α` | 生产者风险（把好人误判全检的概率） | 0.05 |
| `β` | 消费者风险（把差人漏放的概率，"保证"的硬度） | 0.05 |

> 注：业界惯例 `p1 > p0`，本场景"通过率高=好"，故 `p1=0.90` 为合格水平、`p0=0.80` 为拒收水平。

### 判定（针对单个标注员，逐条累计）

设已检 `n` 条、其中**不通过**（缺陷）数为 `d`。建模：H0=好（缺陷率 `q0 = 1-p1 = 0.10`），H1=差（缺陷率 `q1 = 1-p0 = 0.20`）。α=误拒好人、β=漏放差人。

对数似然比累计后，Wald 的两条边界（**注意 α/β 在两条线里的归属，不可对调**）：

- 接收（判好、放行整批）：`LLR ≤ ln(β/(1-α))`
- 拒收（判差、转全检）：`LLR ≥ ln((1-β)/α)`

线性化成对缺陷数 `d` 的直线边界：

- 接收线：`d ≤ a + s·n`
- 拒收线：`d ≥ b + s·n`

其中公共分母 `D = ln(q1/q0) + ln((1-q0)/(1-q1))`：

```
s = ln((1-q0)/(1-q1)) / D          # 斜率
a = ln(β/(1-α)) / D   =  -ln((1-α)/β) / D   # 接收截距（负值）
b = ln((1-β)/α) / D                          # 拒收截距（正值）
```

> 关键：接收线用 `ln(β/(1-α))`（含 α 在分母），拒收线用 `ln((1-β)/α)`（含 α 在分母）。
> 自检（α≠β 时必须成立）：α 越小（越不愿误拒好人）→ `b` 越大 → 越难拒收，保护好人；β 越小（越不愿漏放差人）→ `|a|` 越大 → 越难接收，多抽以抓差人。α=β 时两式数值相等，故旧写法在默认参数下被掩盖。

- 每检一条更新 `n, d`：
  - `d ≤ a + s·n` → **验收通过**，该员剩余不必再检（整批放行）。
  - `d ≥ b + s·n` → **判定不合格**，该员剩余转全量质检。
  - 两者之间 → **继续抽 1 条**（处于"模棱两可"区，本就该多花成本）。
- 起步保护：检不到接收线需要的最小样本前（`n` 很小时 `a+s·n` 可能为负，天然无法接收），SPRT 自动要求多抽，无需额外特判。
- 抽样顺序：优先「未检」，用 promptId 哈希做稳定随机（可复现）。

### 必须的边界处理（上线前必补，缺则退化成全检 / 假抽样）

SPRT 在「真实正确率正好卡在中点」时平均抽样量很大（实测 p≈0.85 时要 ~113~127 条），仅靠"检完整批"对边界标注员等于全检。故引入两条硬规则：

**1. `n_max` 截断 + 到顶判定（解决边界标注员退化为全检）**
- 取 `n_max = min(N, NMAX_CAP)`，`NMAX_CAP` 默认 `100`（页面可调）。
- 检到 `n == n_max` 仍未触线（落在两线之间）时，**强制终判**，不再继续抽：
  - 设中点缺陷率 `q_mid = (q0 + q1) / 2`（默认 `(0.10+0.20)/2 = 0.15`，等价正确率中点 0.85）。
  - 若 `d / n_max ≤ q_mid` → 判 **accept（验收通过）**；否则 → 判 **reject（转全量）**。
- 即：到顶后用经验缺陷率与中点比较收口，把"模棱两可"区强制归到更近的一侧。
- 注：SPRT 两线的中性斜率（似然比=1）为 `s≈0.1452`，与 `q_mid=0.15` 仅差约 0.0048。也可用 `s` 作收口分界（与 SPRT 漂移方向完全对齐、更自洽），二者数值接近、不影响大局。首版用 `q_mid`，此处记一笔避免日后质疑不一致。

**2. 小批量全检兜底（解决 `N` 太小时假装抽样）**
- 取 `N_min` 默认 **`50`**（页面可调）。选 50 是为避开 `[30,~50]` 这段"白检区"——默认参数下最早 accept = 第 25 条，若 `N_min` 太小，`N` 刚过阈值的人要 accept 得检 25 条、占比 70%+，抽检几乎不省。设 `N_min=50` 让抽检只对"真正大批量"的标注员生效。
- 当某标注员 `N < N_min` 时，**直接整批全检**，不跑 SPRT；状态机直接标记为 `full-check`（前端显示「全检」而非「抽样中」），`建议待检 = 该员全部未检条目`。
- 当 `N ≥ N_min` 但 SPRT 自然检完所有条目仍未触线时，按到顶规则（同 `n_max`）收口。

> 这两条不补，边界标注员会退化成全检、小批量会假装抽样——必补项。

### 效果

- **好的人很快放行**：正确率 95% 的人，抽十几条全过即越过接收线，立刻整批放行，不必检满固定批量。
- **差的人很快拦下**：错误密集时迅速越过拒收线，几条即判"转全检"。
- **只有边界附近的人**才被多抽几条——成本花在该花的地方。
- `β` 是可调旋钮：越小"保证"越硬，平均抽样量略升；矛盾被显式量化。

### 输出给前端

每个标注员：`{总数N, 已检n, 不通过d, 通过率, 状态(全检/抽样中/验收通过/转全量), SPRT决策(accept/continue/reject/full-check), 距接收还差几条(估算), 建议下一条待检id}`，外加全局汇总。「建议待检」让质检员一键跳到下一条该检的，最小化点选。

**「建议待检」的终态语义（写死）：** `accept` → 建议待检为**空**（已放行，无需再检）；`reject`/`full-check` → 建议待检 = 该员**全部未检条目**（要全检）；`continue` → 哈希序第一条未检（见「下一条待检挑选顺序」）。

**「距接收还差几条」的特判（写死）：**
- 该员处 `accept` 终态时：显示**终态标识（如"已通过/已放行"）而非数字**，不再显示"还差 0 条"。
- `continue` 态、`n=0`（尚未检任一条）：公式给 25（全过需 25 条）是合理初始预期值，正常显示。`N<N_min` 的人为 `full-check`、不显示此字段。
- 算出负数或不可达时显示 `—`（见下「不可达边界处理」）。

**"距接收还差几条"口径（写死公式）：** continue 态下，取**乐观估计**——假设后续全部通过（`d` 不增），要触接收线 `d ≤ a + s·n'` 所需的最少追加条数为 `ceil((d - a) / s) - n`（结果向下截到 ≥0）。这是乐观值，中途再出错会变多。若已不可能（如已接近 reject、或值算出 ≤0 但实际未触线的边界情形）则显示 `—`，与下面的不可达规则衔接。

**展示层对不可达边界的处理（写死）：** SPRT 的 reject 边界对小 `n` 天然不可达（`b=3.631, s=0.1452`，n=1 需 `d≥4`、n=10 需 `d≥6`，实际不可能），这是 reject 也需最小证据量的正常行为。因此"距拒收还差几条"等估算若算出**负数或不可达**，展示为 `—` 而非负数；"距接收还差几条"同理（n 过小时接收线 `a+s·n` 为负、尚不可接收时显示 `—`）。

### 终态锁定（不可逆）——必须按到达顺序重放，不能只看终点

SPRT 是**序贯**算法，结论依赖逐条到达的顺序，**不是**只看最终累计点 `(n, d)`。`/api/qc-stats` 是事后"读全表、按评测人分组重算"，因此必须**定义唯一的重放顺序**，否则终态不可复现、会算出自相矛盾的结论。

反例（说明为什么不能只看终点）：
- 某员前 25 条全过，在第 25 条已越过接收线 → 应锁定 `accept`。若后面补检 10 条全错，只看最终点 `(35,10)` 会误算成 `reject`——同一个人两种相反结论。终态本意是"第 25 条 accept 后不可逆"，故必须按到达顺序取**首次触线**。
- 同样 `n=27, d=2`，"两个错在最前"是 `continue`，"两个错在最后"是 `accept`（前 25 条已先触接收线）。只看终点对两者都给 `continue`，丢掉了已发生的 accept。

**重放顺序（写死，二选一）：**
1. **优先按 `qcTime` 升序重放**（质检员真实检验顺序）——最贴合"首次触线即锁定"语义，**默认采用**。
2. 若该员存在缺失 `qcTime` 的已检条目，则整组退化为按"建议待检"的 **promptId 哈希顺序**重放：**沿哈希顺序遍历该员全部条目，仅纳入「已检」条目、跳过未检，按纳入次序逐条推进判定**（即上例哈希序 `[c1,c2,c3,c4,c5]`、已检 `c1,c3,c5` 时，判定序列为 `c1→c3→c5`）。**不是**"遇到第一个未检即停"（那会让跳检场景几乎永远 `continue`）。

**两套顺序各司其职、互不冲突（写死，避免实现者困惑"到底用哪个序"）：**
- **判定/终态顺序**（只对【已检】条目有定义）：按 `qcTime` 升序重放。未检条目没有 `qcTime`，天然不参与。
- **"下一条待检"挑选顺序**（只在【未检】条目里挑）：永远按 promptId 哈希序取第一条。因为未检的没有 `qcTime`，挑选必然走哈希序——即使 `qcTime` 正常，挑下一条也用哈希序。
- 仅当该员存在缺 `qcTime` 的已检条目时，判定才整组退化为哈希序重放（此时两套序对齐）。

**`/api/qc-stats` 判定算法（写死）：**
```
if 该员 N < N_min:                                       # 小批量全检兜底，优先于 SPRT
    state = full-check; 建议待检 = 全部未检; 跳过重放
否则按重放顺序遍历该员已检条目，维护 (n, d)：
  每加入一条：n += 1；不通过则 d += 1
  if d ≤ a + s·n:  state = accept;  冻结，break        # 首次触接收线
  if d ≥ b + s·n:  state = reject;  冻结，break        # 首次触拒收线
  if n == n_max:   state = accept if d/n_max ≤ q_mid else reject; 冻结，break
遍历结束仍未冻结：
  if 已检完该员全部条目:  按到顶规则用 d/n 与 q_mid 收口
  else:                   state = continue              # 还能继续抽
冻结后（accept/reject/full-check 为终态）：后续补检条目只累计计数（更新展示用的 n,d/通过率），**不改判定**。
```
> 关键一句：**沿重放顺序逐条推进，一旦触线/到顶立即冻结为终态，绝不能拿最终 `d/n` 套边界。** 实现者切勿顺手写成"拿最终 d/n 比边界"。

**`n_max` 用谁的 n（写死）：** 是"按重放顺序检到第 `n_max` 条时仍未触线 → 在那个前缀点用 `d/n_max` 收口"，**不是**"总已检数到达 `n_max`"。补检导致总数超过 `n_max` 时，以**首次到达 `n_max` 的前缀**为准（与重放冻结同一件事）。

**边界可达性自检（默认参数下已验证自洽，记一笔免日后疑惑）：**
- **最早 accept = 第 25 条**：`-a/s` 恰为 25（默认参数下为整数，巧合但正确）。即前 24 条全过也只能 `continue`，第 25 条才放行——这就是 SPRT 对"好人"要的最小证据量，符合预期，无需额外特判。
- **最早 reject = 第 5 条**：`b/(1-s)≈4.25→5`。即哪怕前几条全错，也要到第 5 条才判转全检，不会"错 1 条就拦"。
- **`N=60` 时 `n_max=min(60,100)=60`**：若该员一路 continue 到检完全部 60 条仍未触线，"检到 n_max 收口"与"检完全部收口"是同一点、同一套 `d/n vs q_mid`，两条规则重合不打架。（`N<N_min=50` 的人直接 `full-check`，不进入此分支。）

> 实现说明：纯算术（log/除法），不依赖外部统计库；`a/b/s` 由四参数唯一确定，逐条判定。接口与上一版"分阶段规则"一致，仅替换判定内核，前后端结构不变。

- 把质检列加入 `writableColumns`。

- row 输出列字母 `qcVerdictColumn` 等，供前端写回定位。

- 入参：`excelRow/recordId`、`sourceUrl`、`verdict`(通过/不通过)、`comment`、`reviewer`(登录名)。
- 一次写 4~5 个质检列 + `已检`标记。复用 `write_source_cell` 多列写入。

- **写回响应顺带返回**：该员重放后的最新状态（`state/n/d/通过率/下一条待检 id`，复用 `/api/qc-stats` 的同一算法），供前端「下一条待检」直接用、不自算。
- **写回顺序（写死）**：**先落库写入 → 再 `clear_runtime_caches(source)` → 再用新数据重算该员状态返回**。响应里的状态必须基于"刚写入这条之后"的最新全表，否则前端拿到的是写入前的旧状态、差一条。
- **软防重**：写回前若该条已存在 `质检人/质检时间`，响应里附 `previousReviewer/previousTime` 供前端软告警（不阻断写入）。

**4. 统计接口**：新增 `/api/qc-stats` GET
- 读全表，按「评测人」分组，**按 `qcTime` 升序逐条重放**套用「终态锁定」算法（首次触线/到顶即冻结，非取终点），返回每个标注员的统计 + 终态/阶段状态 + 建议待检 id 列表 + 全局汇总。
- 缺 `qcTime` 时该组退化为 promptId 哈希顺序重放（见「重放顺序」）。
- 抽检参数（`p1/p0/α/β/NMAX_CAP`默认100/`N_min`默认50）从 query 读（带默认值）。

**5. 模板注册**：A/B 模板增加 `supportsQC: True` 标识，前端据此显示模式切换。

- 显示该行当前 `质检人/质检时间/已检` 状态。
- 「下一条待检」按钮：跳到抽检算法建议的下一条。
- **判定单一来源（写死）**：前端**绝不自行计算 SPRT**。"该员是否还需继续检 / 下一条待检 id / 终态"一律由后端给出——来源为 `/api/qc-stats`，或 `/api/qc` 写回响应里顺带返回的"该员最新状态 + 下一条待检 id"。前端只渲染，避免前后端两套逻辑不一致（出现"前端让你接着检、统计页却显示已 accept"）。
- **软防重提示**：`/api/qc` 写回时若该条已被他人检过，响应返回"该条已被 X 于 T 检过"，前端给二次质检者一个软告警（非强锁，需求 #6）；保存仍允许，但提示会覆盖原结论/质检人/时间。

**4. 质检统计视图**：复用 [renderIssueDistribution](file:///Users/bytedance/Desktop/pe观测/diy/assets/app.js#L1443) 所在的分布页容器，qc 模式下改渲染 `renderQcStats()`：表格列出每个标注员 `总数/已检/通过/不通过/通过率/阶段/建议再抽N条`，顶部全局汇总。

**5. 列表筛选**：qc 模式下，筛选项可加「质检状态：全部/未检/已检/不通过」「按标注员」，复用现有筛选框位置；首版至少支持「未检」过滤以配合抽检。

## 已知前提与后续排期（首版不阻塞，需有意识）

这些不阻塞上线（`n_max` 截断与小批量全检兜底已纳入算法必补项），但要写进文档避免被默认值掩盖：

1. **质检员 = 真值**：`/api/qc` 直接采信质检员判断，无校准。后续可埋少量 gold set 或抽样复检校准质检员本身——**首版至少预留接口位**（如 `/api/qc` 接受 `goldCheck` 标记字段，统计接口预留质检员准确率口径）。
2. **i.i.d. 假设**：按单人整批跑一条 SPRT，假设缺陷独立同分布。但错误常按标签类目聚集，违反独立性会让 β 实际偏大。后续建议**按类目分层**跑 SPRT，或在文档显式标注此前提（首版先文档标注）。
3. **缺陷不分级**：当前二值 通过/不通过。后续可对 critical/major 设不同 `q0/q1`，分级跑。首版保持二值。
4. **终态锁定已纳入**（见上「终态锁定」节）。
5. **并发派发不做锁（首版仅注明）**：`/api/qc-stats` 给每个 continue 态标注员返回单个"下一条待检 id"（哈希序第一条未检）。两个质检员同时打开统计页会拿到同一条、可能撞车白检（写锁保证不串数据，仅是重复劳动）。1~2 人无所谓，5+ 人值得后续改成"返回哈希序前 N 条队列、前端本地游标错开"。首版不做派发锁。

### 三个工程提醒（实现时落地）

- **`/api/qc-stats` 性能**：每次读全表，标注量大时会慢。首版可接受，但加 TTL 缓存（复用现有 `_ROWS_CACHE`/`ROWS_CACHE_TTL_SECONDS` 机制）或增量；写回后 `clear_runtime_caches(source)` 失效缓存。
- **质检人身份**：localStorage 清缓存即丢且无法防冒名。`qcReviewer` 最好跟登录态对齐；首版至少在 `/api/qc` 校验 `reviewer` 非空，并在响应里回显本次写入的 `qcReviewer` 供前端核对。
- **并发写回串行化 + 软防重**：多人写同一表，`已检` 标记可能因竞态丢失。确认 `write_source_cell`/`run_lark sheets +write` 路径加进程内写锁（如 `_WRITE_LOCK = threading.Lock()` 包住一次多列写入），保证 `已检` 标记与质检列原子提交。写锁只保证单次写入原子，**不防同一条被两人先后各检一次**——第二次会覆盖结论/质检人/时间。统计按 promptId 去重取最后一次，逻辑不崩；首版不上强锁，仅在 `/api/qc` 返回 `previousReviewer/previousTime` 让前端软告警。

## 验证
1. 启动 `python3 lark_server.py`，加载 A/B 表，输入质检人名字。
2. 切到质检模式：详情页出现 通过/不通过 + 意见 + 保存。
3. 保存后用 `lark-cli sheets +read` 复查新列（质检结论/意见/质检人/时间/已检）已写入；自动建列生效。
4. 多名（模拟换名字）质检若干条，打开质检统计页：核对每个标注员 总数/已检/通过率/阶段/建议再抽条数 是否符合抽检算法。
5. 抽检算法验证：构造某标注员通过率高（应「整批放行」）、某标注员通过率低（应「转全量」），确认阶段判定正确。
6. 边界规则验证：构造正确率卡 0.85 的标注员（`N≥N_min`），确认检到 `n_max` 即按 `d/n_max` 与 `q_mid(=0.15)` 比较强制终判，不再无限抽；构造 `N<50` 的标注员，确认状态直接「全检」、`建议待检`=全部未检。
7. 终态锁定验证：某员判 accept 后再补检一条不通过，确认状态仍为「验收通过」不回退到「抽样中」。
8. 防重复：已检条目在列表「未检」筛选下不再出现；详情页显示已检状态。
9. 回归：PE 模板加载与标注/划线功能不受影响。
